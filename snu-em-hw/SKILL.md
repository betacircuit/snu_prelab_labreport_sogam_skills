# 기초전자기학 및 연습(기전연) — MATLAB 과제 (HW)

실험 보고서가 아니라 **과제**다. prelab·lab report 절차(evidence.yaml, 실험 방법, 토론)는 쓰지 않는다.
내는 것은 `HW1.m`(MATLAB 코드)과 결과 보고서 PDF를 묶은 zip 하나다. 규칙은 `references/course.md`.

- **공통 엔진을 읽는다: `../snu-report-core/SKILL.md`** (저장소에서는 `snu-report-core/SKILL.md`). 서식·문체·오탈자 검사·빌드는 엔진 것을 쓰고, `$E`는 엔진 `scripts/` 절대 경로다.
- 작업 폴더의 `courses/em/hwNN/`에 쌓이고, 실습 자료 PDF·skeleton·`HW1.m`·MATLAB 캡처는 `inbox/em/`에 넣는다. **실습 N 자료의 Homework = HW N** (파일명·내용의 `실습1`, `HW1`, `과제 1`로 분류).
- 과제는 실습 자료 PDF 끝의 **Homework** 절(문제 1., 2., 3.)과 **eTL 제출** 쪽, 마감은 앞쪽 "제출 기한"에 있다.
- 쓰기 전에 `references/mistakes.md`(MATLAB·전자기 실수)와 엔진의 공통 `references/mistakes.md`를 읽는다.

공통 엔진의 **실행 호스트 분기**를 먼저 적용한다. Codex는 runtime-codex.md, Claude는 runtime-claude.md만 읽는다.

## 이 과목에서 엔진 규칙과 다른 것 (사용자 지정 — 어기면 안 된다)
1. **코드는 MATLAB 화면 사진으로만 넣는다.** 보고서에 MATLAB 코드를 글자(코드 블록)로 넣지 않는다. 빌드가 `{{code:}}`와 ``` 블록을 막는다.
2. **MATLAB 코드를 내가 쓰거나 고치지 않는다.** 코드·주석·결과는 전부 본인(학생)이 MATLAB에서 만든 것이다. `HW1.m`은 받은 그대로 zip에 넣는다.
   `mcode.py check`에 걸린 것(첫 줄, 한글 주석, 금지 함수, 빠진 조건)은 **채팅으로 알리고 본인이 고치기를 기다린다** — 내가 고친 코드를 보고서나 zip에 넣지 않는다.
3. **코드와 결과는 본인이 직접 찍어 올린 사진으로만.** 문제마다 코드 화면 사진과 실행 결과 사진을 본인에게 받는다. 사진이 오기 전에는 **한 줄 누락 표시**를 넣어 초안을 만든다. 대신 그리거나 코드를 돌려 만든 그림으로 채우지 않는다. 빌드가 문제마다 두 사진 자리가 있는지 확인한다.
   **컬러 그대로** 넣는다: MATLAB이 그린 파란 선, 편집기의 초록 주석 색 그대로. 엔진의 "흑백만" 규칙은 기전연에 쓰지 않는다.
4. **본인이 쓴 글로.** 보고서에 "사용자", "AI", "제공된", "캡처/촬영한", "수정 전/후 코드", "원본 코드" 같은 말을 쓰지 않는다. 본인이 한 일은 주어 없이 "~했다". 그림 캡션도 "Problem 1 코드", "Problem 1 결과". 빌드가 이런 말을 막는다 (`[본인 글]`).
5. **수식은 짧게, 긴 식은 줄을 바꿔서** (아래 "수식"). 빌드가 단위·함수 이름을 세움꼴로 바꾸고 크기를 맞추지만, 줄 배치는 원고에서 정한다.

## 폴더
```
courses/em/hw01/
├── meta.yaml          hw: 1, title: 과제 주제, due: 제출 기한
├── requirements.md    문제·제약 목록과 대응표
├── materials/         실습 자료 PDF (+ .txt), skeleton
├── code/HW1.m         제출 코드 (본인 파일 그대로)
├── figs/              MATLAB 화면 사진 (p1_code.png, p1_result.png …)
├── hw.md              보고서 원고
└── build/             HW1_이름_학번.docx / .pdf / .zip
```

## 작업 순서
0. `python $E/setup_profile.py --check --course em` — 빠진 것(이름, 학번)만 묻는다. 조는 묻지 않는다.
   **첫 메시지에서 사진을 한 번에 요청한다** (이름·학번을 물을 때 같이). 실습 PDF를 먼저 읽어 문제 수를 알고 아래를 채워 보낸다:
   ```
   문제마다 MATLAB 화면을 찍어서 올려 줘 (Windows: Win + Shift + S, Mac: Cmd + Shift + 4).
   - 코드: 편집기에서 그 문제 부분 전체 (줄 번호와 주석까지 보이게, 길면 여러 장)
   - 결과: figure 창 전체 (그래프 색 그대로), 값을 출력했으면 명령 창도
   - 파일 이름 예: p1_code.png, p1_result.png, p2_code.png … (아니어도 내가 보고 정리함)
   - 그리고 제출할 HW1.m 파일
   문제: 1) …  2) …  3) …   ← 실습 자료의 문제를 한 줄씩
   ```
   사진 없이 작성할 수 있는 부분으로 초안을 만든다. 사진 자리는 한 줄 표시로 남기고 사진 요청 목록을 같이 보낸다.
1. `python $E/ingest.py` → `courses/em/hw01/`. Homework의 문제·제약·제출 기한이 `requirements.md`와 `meta.yaml`에 초안으로 들어가고, 사진은 `figs/`, `.m`은 `code/`로 간다.
   - PDF 원문과 대조해 문제를 빠짐없이 옮기고, **문제마다 제약**(예: "내장 sinc 사용 금지", "subplot 사용하지 않고", "5개 이상의 그래프", "30x30 행렬")을 한 줄씩 적는다. `meta.yaml`의 `title`을 채운다.
2. **사진 정리**: `figs/`의 사진을 하나씩 열어 보고 문제별로 이름을 바꾼다 — `p1_code.png`(코드 화면), `p1_result.png`(결과 그림), 여러 장이면 `p1_code_2.png`. 무엇인지 모르겠으면 한 번 묻는다.
   - 문제마다 코드 사진과 결과 사진이 있어야 한다. 빠진 것은 "문제 2 결과 그림 사진을 올려 줘"처럼 **한 번에 모아서** 달라고 하고, 그 자리는 한 줄 누락 표시로 둔다. 대신 그리거나 코드를 쓰지 않는다.
   - 사진 속 그래프가 흐리거나 잘렸으면 다시 찍어 달라고 한다 (figure 창을 키워서, 코드는 글자가 읽히게).
3. **코드 검사 (고치지 않는다)**
   - `HW1.m`이 있으면 `python $E/mcode.py check courses/em/hw01/code/HW1.m --problems 1 2 3 --forbid "1:sinc,subplot"`.
   - 사진으로 과제 조건도 대조한다 (예: 그래프 5개 이상인가, subplot을 안 썼나, 3x1인가).
   - 걸린 것은 채팅으로 한 번에 알린다: "문제 1: 표본 간격이 한 가지뿐이라 '5개 이상' 조건에 안 맞음" 식으로. 본인이 고쳐서 새 사진·파일을 주면 그걸 쓴다. 보고서는 받은 코드 그대로 설명한다.
   - `HW1.m` 파일이 없고 사진만 있으면 zip에 넣을 `HW1.m`을 달라고 한 줄 알린다 (사진을 옮겨 쳐서 만들지 않는다).
4. **수치**: 결과 사진(그림, 명령 창)에 보이는 값만 쓴다. 지어내지 않는다. `mcode.py run`은 본인 코드가 에러 없이 도는지 확인할 때만 쓰고, 그 그림은 보고서에 넣지 않는다.
5. **보고서 `hw.md`** (`templates/hw.md` 뼈대) — 사진이 오기 전에 **예상되는 사진을 기준으로 먼저 쓴다**. 문제마다 절 하나 `# Problem 1) …`:
   - 사진 자리: `![Problem 1 코드](figs/p1_code.png){#fig:p1code width=100% hint="편집기에서 %% Problem 1 절 전체 (줄 번호·주석 보이게)"}` — 파일이 없으면 한 줄 누락 표시를 넣고 `hint`는 별도 촬영 요청 목록에만 적는다. 사진이 오면 같은 이름으로 `figs/`에 두고 다시 빌드한다.
   - 문제 풀이 방법, 식, 과제가 요구한 서술처럼 사진 없이 쓸 수 있는 것은 먼저 다 쓴다.
   - 사진을 봐야 확정되는 문장(코드 동작 원리의 세부, 결과 수치·해석)은 `[확인 필요: 사진 받은 뒤 — 무엇을 확인할지]`로 둔다. 빌드가 노란 형광펜으로 칠한다. 사진이 오면 사진 속 코드·결과대로 채우고 지운다.
   1. 풀이 방법 — 쓰는 식 (아래 "수식")
   2. 코드 — 코드 화면 사진: `![Problem 1 코드](figs/p1_code.png){#fig:p1code width=100%}` (글자 코드는 넣지 않는다)
   3. 코드 동작 원리 — 과제 요구 항목. 사진 속 코드와 주석을 읽고, 계산 순서와 이유(왜 이 간격·이 조건·이 함수)를 본인이 설명하듯 쓴다. 줄마다 읽어 주지 않는다. 코드에 없는 동작을 지어내지 않는다
   4. 결과 — 결과 캡처 `![…](figs/p1_result.png){#fig:p1 width=85%}`와 해석, 문제가 요구한 서술(예: 간격이 좁을 때와 넓을 때의 장단점)
   - 학번·이름은 제목 블록에 자동으로 들어간다.
6. `python $E/build.py courses/em/hw01 hw --pdf`
   - 문체·오탈자·수식 배치·코드 검사를 같이 돌린다. `[수식]` 경고는 전부 고친다.
   - 빌드가 멈추는 경우: 글자 코드, `[본인 글]` 표현. 사진 파일이 없으면 초안에는 한 줄 표시를 넣고 받아야 할 사진 목록을 보여 준다 (`--final`이면 멈춘다).
   - 누락 표시나 `[확인 필요]`가 남아 있으면 제출용 zip은 만들지 않는다. 사진과 `HW1.m`이 다 오면 Homework 원문 범위와 문제별 답변을 `requirements.yaml`의 `scope.hw`, `kind: hw` 문항으로 기록하고 `--final`로 다시 빌드한다.
   - 생성물은 `out/drafts/em/`의 초안이며, PDF를 생성했더라도 아직 최종 전달본은 아니다.
7. 선택한 호스트의 `quality.py render`로 실제 DOCX를 렌더링하고 모든 쪽을 **직접 읽어** 아래 항목을 대조한다. `quality.py review <DOCX> --pages 1,2,...` → `quality.py deliver <DOCX> --lab-dir courses/em/hw01 --kind hw`를 통과하면 `out/em/`에 검토한 DOCX·PDF·원본 `HW1.m`·zip이 생긴다.
   - 렌더링이 불가능하면 초안 DOCX와 본인 코드 파일을 주고 미검증 부분을 알린다. 사용자가 Word에서 PDF를 저장해 직접 묶으려는 경우에는 기존 `mcode.py pack ... --pdf <PDF>`를 쓸 수 있으며, 이를 AI의 렌더링 검증 완료로 주장하지 않는다.

## 수식
문장 속 수식은 기호와 짧은 식만. 분수·괄호 나눗셈·긴 식은 문장을 끝내고 다음 줄에 `$$…$$`로 뺀다. 따로 뺀 줄에는 식 하나(많아야 둘).
```
정규화 sinc 함수는 다음과 같다.

$$\operatorname{sinc}(t) = \frac{\sin(\pi t)}{\pi t} \quad (t \neq 0), \qquad \operatorname{sinc}(0) = 1$$

표본 수가 $N$이면 간격은 다음과 같다.

$$\Delta t = \frac{4\pi}{N - 1}$$
```
- 여러 성분 식(`E_x`, `E_y`, `r`, `k`)은 한 줄에 몰지 않고 두 줄 이상으로 나눈다.
- 단위는 `\ \mathrm{V/m}`처럼 세움꼴 (빠뜨려도 빌드가 숫자 뒤 단위를 세운다). 함수는 `\sin`, `\sinh`, `\operatorname{sinc}`.
- 수치 결과는 수식보다 글로: "전기장 크기는 $8.99 \times 10^{9}\ \mathrm{V/m}$였다" 정도로 짧게.
